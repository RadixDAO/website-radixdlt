<p id=""><em id="">Opinion Post by Josh Primero, Head Protocol Architect at RDX&nbsp;Works</em></p><p id="">In my <a id="" href="https://www.radixdlt.com/blog/how-radix-engine-avoids-the-flaws-of-suis-movevm">previous article</a>, I went over how Radix Engine avoided some of the flaws in Sui’s MoveVM. To summarize:</p><ul id=""><li id="">Sui’s MoveVM is too low-level and generic, making for a cumbersome DeFi programming environment.</li><li id="">Radix Engine is high-level and asset + business logic oriented, allowing developers to focus on DeFi logic rather than low level details.<br>‍</li></ul><p id="">Sui’s MoveVM follows the original <a id="" href="https://ethereumbuilders.gitbooks.io/guide/content/en/design_rationale.html">Ethereum philosophy</a> of a “clean, simple, beautiful” protocol which delegates everything to the application layer. This allows developers the freedom to explore any domain, including unknown ones at the time.</p><p id="">A protocol which is too simple and unstructured, though, creates significant compromises. For example, common system features like authorization would require a complex implementation in the application space, standard interfaces may become more fragmented, and performance optimization becomes more difficult.</p><p id="">Radix Engine, on the other hand, is designed to execute non-generic, system-wide logic as a core technical goal as it allows us to do the following:</p><ul id=""><li id=""><em id="">Enforce system-wide standards/implementations</em>. An opinionated standard allows for development/maintainability/tooling to be easier across the stack as apis are not fragmented (e.g. ERC-20 vs ERC-721 vs ERC-404) and understanding behavior does not require bytecode interpretation (no more ERC-20 rugpulls). This gives developers and end users a safer, more consistent DeFi experience.</li><li id=""><em id="">Execute logic closer to hardware</em>. As system logic doesn’t need to be run by an interpreter for correctness, execution of that logic can be run as close to hardware as possible.</li><li id=""><em id="">Parallelize execution. </em>By having in-hand knowledge of the behavior of certain objects it’s easier to make static analysis decisions before execution allowing for parallel execution.<br>‍</li></ul><p id="">Vitalik recently touched on this idea with the term “<a id="" href="https://vitalik.eth.limo/general/2023/09/30/enshrinement.html">enshrinement</a>”, or the idea of selectively breaking away from abstraction in order to gain benefits of protocol-enforced logic. Stealing one of his images, he frames the problem as a tradeoff between abstraction vs. enshrinement:</p><p id="">‍</p><figure id="" class="w-richtext-figure-type-image w-richtext-align-fullwidth" style="max-width:781px" data-rt-type="image" data-rt-align="fullwidth" data-rt-max-width="781px"><div id=""><img id="" alt="" src="/assets/66140bd1a3c1e015fb07b97a_PmMRW8C_Da5uFbSSuLFQwgTD9rKPY2TqQRe1bF1MyWOHjp7ouMgsftsjOuPLXFtZJPPzuZR_BJNA0pbd7a8vj2M68G_f1Mp4FF72WOWmHVL4NxPaY_W-yfp9pzuXcnhGRlIZ24cjGPPjQ9BSwpHqfCA.png" width="auto" height="auto" loading="auto"></div><figcaption id=""><em id="">Vitalik’s abstraction vs. enshrinement tradeoff</em></figcaption></figure><p id="">This balance of supporting abstraction (i.e. future/diverse user needs) while maintaining performance/security/usability (i.e. enshrinement) is actually a very old computer science problem. The design of Operating Systems specifically has been trying to solve a similar problem for decades: How do we support a range of abstract applications while maintaining a fast, secure, usable system?</p><p id="">In this article I will go over how Radix Engine uses the Operating System model to create a framework capable of all types of “enshrinement” without the load to protocol complexity or loss of flexibility that Vitalik fears.</p><p id="">Let’s start by looking at the current industry standard, the Ethereum Virtual Machine (“EVM”).</p><h2 id="">EVM as a VM</h2><p id="">The EVM is basic enough that it can be modeled as a virtual machine (“VM”) with the following opcodes:</p><ul id=""><li id="">Turing-complete opcode set</li><li id="">Opcodes for calls to other smart contracts</li><li id="">Opcodes for reading/writing to persistent storage owned by the current smart contract<br>‍</li></ul><p id="">Smart contracts compiled into EVM bytecode can then be executed on top of such a VM.</p><figure id="" class="w-richtext-figure-type-image w-richtext-align-fullwidth" style="max-width:940px" data-rt-type="image" data-rt-align="fullwidth" data-rt-max-width="940px"><div id=""><img id="" alt="" src="/assets/66140bd0ffa7e587b728998d_38xkWltrZdRRy2gLfk_RE_1wLmv-XL67J0WtBjo2mArrNwzAmfmQGMCKpjSTfX0lf_wS8DbBIPia4tMnvxqTuAmpvfhZ6tubk8L1rSJzYv1gyZT2HoNo4r_ePFJrVl_RrK2aCvtqbcU9uKXVp8la8uY.png" width="auto" height="auto" loading="auto"></div><figcaption id=""><em id="">EVM model</em></figcaption></figure><p id="">In this model, any form of “enshrinement” requires changes to the EVM, or the VM hardware. For example, enshrining BLS signature support would require adding a new precompile. Or implementing <a id="" href="https://eips.ethereum.org/EIPS/eip-2938">EIP-2938</a> would require the addition of new opcodes. Expanding on what is enshrined inevitably results in a larger, more complicated VM and forces the protocol designer into the <em id="">choose one-or-the-other</em> decision Vitalik describes.</p><p id="">‍</p><figure id="" class="w-richtext-figure-type-image w-richtext-align-fullwidth" style="max-width:946px" data-rt-type="image" data-rt-align="fullwidth" data-rt-max-width="946px"><div id=""><img id="" alt="" src="/assets/66140bd164027dd295d4be4a_5jL-_dzLRpdb2uQP53J2J5sXczxxqKCseXe1RttXB2nc5KIzYKJ1s3vyfZUD30jRzL4XCo18k0WEkuVQ8PxrQ26QNNojlSZR2wxbIzSGM8nmXM-XN8ai_R1ZhK5VV9UKkxn9OWE6C74MKcCOrRPDh7U.png" width="auto" height="auto" loading="auto"></div><figcaption id=""><em id="">Enshrinement in the EVM model</em></figcaption></figure><p id="">The general problem with this model is that the Abstraction/Enshrinement dichotomy is too coupled with the Software/Hardware dichotomy. That is, enshrining any logic into the protocol forces it to be embedded into the VM. There is no way to express “enshrined software” or software which is part of the system.</p><p id="">Operating Systems solved this dichotomy with the notion of “system software”. </p><p id="">Let’s take a closer look.</p><h2 id="">The Operating System Model</h2><p id="">One of the main goals of an Operating System is to manage the software/hardware dichotomy – or more specifically the application/hardware dichotomy. The core part of any Operating System is the kernel, software which manages user space applications and their access to hardware. Kernel modules and drivers are additional pieces of system software that expand the set of supported hardware or extend kernel functionality.</p><figure id="" class="w-richtext-figure-type-image w-richtext-align-fullwidth" style="max-width:998px" data-rt-type="image" data-rt-align="fullwidth" data-rt-max-width="998px"><div id=""><img id="" alt="" src="/assets/66140bd0c354fe801fb77089_oyRNB63McFoPzbgMOqj705_zMcwbSABvLWF4dVm_Xx2bAuOHESB6nq6JcJAO_nztF-_P0NLlLWhVJ5MM5ZVn0UxZyuINhaNoIqCpSSco1io9Rm1xaSmpQzAuxY5hcFfzN196allBO2EMVugjWRQ-jzs.jpeg" width="auto" height="auto" loading="auto"></div><figcaption id=""><em id="">Operating System Model</em></figcaption></figure><p id="">From an “enshrinement” perspective, the kernel and its modules are enshrined parts of the system, but have the flexibility of software. Kernel modules, virtual machines (“VMs”), and user-space system processes are even more “soft” since these are abstracted from the kernel itself.</p><figure id="" class="w-richtext-figure-type-image w-richtext-align-fullwidth" style="max-width:1153px" data-rt-type="image" data-rt-align="fullwidth" data-rt-max-width="1153px"><div id=""><img id="" alt="" src="/assets/66140bd186c8f329794f2754_cGp-AmSIGyxDu12UHiGqRnRhQiJ9TUN7lFMezAJY4rnAdH5yRvVi6_zg5S9oPkYV4K56vTMmfelgycT_7CYMcfEyjGVKC7INYcwiTwvCNC38fqPiDtvMtmQwfXtsG4LumIwDFXStsgbm1OeDpxlYHWU.jpeg" width="auto" height="auto" loading="auto"></div><figcaption id=""><em id="">Enshrinement in the Operating System Model</em></figcaption></figure><p id="">In this model, the layer of indirection between applications and hardware allows the software/hardware dichotomy to be decoupled from the abstraction/enshrinement dichotomy.</p><p id="">“System software” allows for enshrinement without overburdening the hardware.</p><h2 id="">Radix Engine as an Operating System</h2><p id="">Using this Operating System model as inspiration, Radix Engine includes multiple layers where each layer has specific responsibilities and abstractions allowing for system modularity and pluggability.</p><figure id="" class="w-richtext-figure-type-image w-richtext-align-fullwidth" style="max-width:944px" data-rt-type="image" data-rt-align="fullwidth" data-rt-max-width="944px"><div id=""><img id="" alt="" src="/assets/66140bd1bd3b87c0857ce3e4_5aWbL6Gaivl14KLmXJ6vGwUXs5qDWV48L3wXROr05NNLo1yC58xeHjnZhTum7kLFjPRzlQ5i6RSSZnhHMTSus1XVqg-JHrJbZ9ORqL4WR5Y0rHDjmX6Z6xdIVIxYdKyNsnbEUfQ7rYNA1-xQIyIRzCY.png" width="auto" height="auto" loading="auto"></div><figcaption id=""><em id="">Radix Engine Layers</em></figcaption></figure><p id="">Such a modular design allows for system logic to be enforced while also allowing the following:</p><ul id=""><li id=""><em id="">Inherit the isolation properties of the layer it’s in</em>. For example, an enshrined package, though enshrined, cannot access arbitrary state but must follow application layer bounds. This is a similar type of security seen in user-space drivers or microkernel design. That is, risk is mitigated by isolating each part of the system so that any updates in the system (enshrinement) do not expose the entire system to risk.</li><li id=""><em id="">Access the features of the layer it’s in. </em>For example, an enshrined package can inherit auth and/or upgradability features provided by the system.</li><li id=""><em id="">Decouple governance. </em>This modular design allows innovation to each of these modules to occur in parallel and at different paces.<br>‍</li></ul><p id="">Let’s now go over each of these layers and see what their responsibilities are.</p><h3 id="">Application Layer</h3><p id="">The application layer is responsible for defining high level logic. Bytecode that describes this logic, along with other static information, is bundled up in an executable format called a Package. Packages are then stored on-ledger and available for execution.</p><p id="">Applications written in Scrypto, the Rust-based language we’ve built for DeFi development, live in this layer. Scrypto programs get compiled into WASM programs with access to a set of function exports which allows the program to access system/kernel services. This <a id="" href="https://github.com/radixdlt/radixdlt-scrypto/blob/main/scrypto/src/engine/wasm_api.rs">System Call API</a> is similar to the Linux <a id="" href="https://man7.org/linux/man-pages/man2/syscalls.2.html">system calls</a> which provide access to shared I/O.</p><h3 id="">VM Layer</h3><p id="">Moving to the next layer down, the VM Layer is responsible for providing the computing environment to the application layer. This includes a Turing-complete VM as well as the interface to access the system layer.</p><p id="">Radix Engine currently supports two VMs: a Scrypto WASM VM used to execute Scrypto applications and a native VM which executes native packages which are compiled to the host’s environment.</p><p id="">If we take a look at the Scrypto WASM VM specifically it looks like:</p><figure id="" class="w-richtext-figure-type-image w-richtext-align-fullwidth" style="max-width:946px" data-rt-type="image" data-rt-align="fullwidth" data-rt-max-width="946px"><div id=""><img id="" alt="" src="/assets/66140bd08f9536aac2376deb_Kk_2LyP64_hUFouJ2WA_wAW1wXl2-DjRnadKQcphb0Xcd0OtIZ5coGi2ewhYXLY244BZtT_13pJ6QpuB5rmQ6uiPrGQfBUh06Hw6RONZaf9vfdxewppHZgjB13FGJl4OAKtTQGUqU_GPndkBDdFJlgs.png" width="auto" height="auto" loading="auto"></div><figcaption id=""><em id="">Scrypto WASM VM Model</em></figcaption></figure><p id="">This may look essentially the same as the EVM model but there are two crucial differences:</p><ul id=""><li id=""><em id="">Removal of direct access to storage. </em>Rather than each smart contract being able to access only its owned storage, any state read/write is done through system calls. This layer of indirection allows many interesting things to be implemented in the system such as state sharing across applications, state virtualization, etc. This layer of indirection is similar to the indirection provided by <a id="" href="https://en.wikipedia.org/wiki/Virtual_memory">virtual memory</a> or Linux’s <a id="" href="https://en.wikipedia.org/wiki/File_descriptor">file descriptors</a>.</li><li id=""><em id="">Addition of system calls</em>. System calls are the mechanism by which the application layer can access services of the System layer such as making invocations to other applications or writing data to an object. These system calls are similar to software interrupt instructions in real CPUs (e.g. <a id="" href="https://en.wikipedia.org/wiki/INT_(x86_instruction)#:~:text=INT%20is%20an%20assembly%20language,INT%20X">INT</a> instruction in x86).<br>‍</li></ul><h3 id="">System Layer</h3><p id="">The System Layer is responsible for maintaining a set of System Modules, or pluggable software which can extend the functionality of the system. These are similar to Linux’s <a id="" href="https://wiki.archlinux.org/title/Kernel_module">kernel modules</a>.</p><p id="">On every system call, each system module gets called before the system layer passes control to the kernel layer. When called, each system module may update some particular state (e.g. update fees spent) or panic to end the transaction (e.g. if the type checker fails).</p><p id="">This pattern allows functionality such as authorization, royalties or type checking to be implemented by the system while being decoupled from both the application and kernel layers.</p><figure id="" class="w-richtext-figure-type-image w-richtext-align-fullwidth" style="max-width:946px" data-rt-type="image" data-rt-align="fullwidth" data-rt-max-width="946px"><div id=""><img id="" alt="" src="/assets/66140bd0e9449b73a0c44f2d_F0QkGCVF_f2_sW1eHZql0qHSog9y62NQu-mL8Ok3-riRJ7sYlrDxa10PyzovYv9eP-0k_l9vXrls4GX29r75ZGN9xdoeWteOAww4Md0XWiU55bh5RjDcJ0UIlJ1P8kE05jAB9kKX7RggJ7_dLTclK-Q.png" width="auto" height="auto" loading="auto"></div><figcaption id=""><em id="">A System Call must pass through the filters of several system modules before being passed onto the kernel</em></figcaption></figure><h3 id="">Kernel Layer</h3><p id="">The kernel layer is responsible for the two core functionalities of Radix Engine: storage access and communication between applications. This is somewhat similar to the traditional Operating System’s responsibility for disk and network access.</p><p id="">For Radix Engine, this includes the following low-level management:</p><ul id=""><li id=""><em id="">Check that move/borrow semantics are maintained on any invocation or data write. </em>The single owner rule and borrow rules are enforced by the kernel. On failure on any of these rules, the transaction will panic.</li><li id=""><em id="">Manage transient vs. persistent objects. </em>An object at any point in time may be in the global space or may be owned by a call frame. The kernel maintains correct pointers to these objects during runtime as references to these objects are passed around.</li><li id=""><em id="">Manage transaction state updates. </em>The kernel keeps track of the state updates which have occurred during a transaction and which will be subsequently committed to the database at the end of the transaction.<br>‍</li></ul><h2 id="">Enshrined Software</h2><p id="">How do these layers relate to enshrinement in a DLT protocol? Similar to the kernel layer in Operating Systems, these middle layers of Radix Engine provide the indirection required to decouple the abstraction/enshrinement dichotomy from the software/hardware dichotomy and create the notion of “enshrined software”.</p><figure id="" class="w-richtext-figure-type-image w-richtext-align-fullwidth" style="max-width:957px" data-rt-type="image" data-rt-align="fullwidth" data-rt-max-width="957px"><div id=""><img id="" alt="" src="/assets/66140bd085c40c1eb6f13305_mYRp3FAgAZaDFqGUbRtiIebc9SsDauVjJZlOIXuooZ-hHfp3FSr8YM3XXo7DkYS6n_bANLB_uOvU6h_UgrDXkJK_5xZsoFfqPN_xXwTd9Rsfpvks3ZIjzQYKaz1pREkBW87FhmSag03ZFBiHwnVU2RQ.jpeg" width="auto" height="auto" loading="auto"></div><figcaption id=""><em id="">Decoupling of abstraction/enshrinement vs. software/hardware</em></figcaption></figure><p id="">Enshrined software has the flexibility and security properties of software while maintaining the ability to enforce system-wide logic.</p><figure id="" class="w-richtext-figure-type-image w-richtext-align-fullwidth" style="max-width:1087px" data-rt-type="image" data-rt-align="fullwidth" data-rt-max-width="1087px"><div id=""><img id="" alt="" src="/assets/66140bd0357934f7ed6f5cd8_4M1JqwZrdnlTFYRuVT_qM-1ROmKroS7b8UFkQzYyU9fqwUH1mqiHCnkbzcKGFQ19siBQACKefsHD_8o6z13YL1rOlYfzPp1V4jdf4TrLAixf8k4W2STrlilZ8fCJJgIw4aOqeM5MpEB4bwsomTgC0ZQ.png" width="auto" height="auto" loading="auto"></div><figcaption id=""><em id="">Radix Engine’s Enshrined Software</em></figcaption></figure><p id="">Let’s go over a few enshrinement examples that are currently running on the Radix network and see how they are implemented.</p><h3 id="">Enshrined Resources</h3><p id="">The core differentiator of the Radix DeFi/Web3 platform is the idea that a resource (i.e. asset) is a fundamental primitive which should be understood separately from business logic. Enshrining this concept allows all dApps, wallets and tooling to have a common understanding of what an asset’s interface and behavior looks like making composability much easier.</p><p id="">Though resources are one of the most ingrained parts of the system, implementing its enshrinement only requires two modular pieces of software:</p><ul id=""><li id="">A native package which handles the logic of resource objects such as Buckets, Vaults and Proofs</li><li id="">A system module which enforces the lifetime invariants of these objects (such as the movability and burnability of resources)<br>‍</li></ul><figure id="" class="w-richtext-figure-type-image w-richtext-align-fullwidth" style="max-width:1087px" data-rt-type="image" data-rt-align="fullwidth" data-rt-max-width="1087px"><div id=""><img id="" alt="" src="/assets/66140bd1bd3b87c0857ce3eb_6Db8Ir5jXigjGI15JQiWjjVWJJo1KUqfnsFwEhnOe_dBHmbH3rbvZIKG_b6i0cI7QkOzVis62q_ycJGma4fwyn2ZBz77XuXCfQLxtvrhefvpXfq9lrvKCBFzK7GFF-iHKYTdk7siwGJ6HNhAw_3gQcg.png" width="auto" height="auto" loading="auto"></div><figcaption id=""><em id="">Radix Engine’s Enshrined Resources</em></figcaption></figure><p id="">The fact that Radix Engine could express the deep concept of a standardized, movable resource while being abstracted from the system/kernel shows the power of a modular system software framework.</p><h3 id="">Enshrined Authorization and Royalties</h3><p id="">Radix Engine standardizes authorization and royalties by decoupling this logic from business logic and implementing these as system features. This allows users and developers to have a built-in common way of understanding the requirements to access any function on-ledger.</p><p id="">The modularity from decoupling business logic from system logic also allows for convenient development/debugging options like the ability to preview a transaction without the normal auth checks (want to simulate the result of sending 10 million USDC somewhere? With authorization disabled, your preview transaction can do the minting!).</p><p id="">Enshrining auth and royalties requires four pieces of modular software:</p><ul id=""><li id="">Auth and Royalties native packages which allow the application layer to access the auth/royalties of any object (for example, to retrieve the auth rule to access a method or to claim royalties).</li><li id="">Auth and Royalties system modules which get called before an object method call to verify whether the caller has sufficient authorization to make the call and to collect royalties.<br>‍</li></ul><figure id="" class="w-richtext-figure-type-image w-richtext-align-fullwidth" style="max-width:1087px" data-rt-type="image" data-rt-align="fullwidth" data-rt-max-width="1087px"><div id=""><img id="" alt="" src="/assets/66140bd047498e763ed1708e_PmJWW2vXXa6zVnj6SmeqZVw6DoaYHVpa2QyZUvR-4FOQ54d4oQ37sN1utg_PLSkyzTlFoPJ2BKi_Oshsd7Dt-jN8JwsNm_-zIQodc-D1cS1ZdEGCuCk5Kb94bt9UEaTH3iThCTerkePRwHbU6qM_QWY.png" width="auto" height="auto" loading="auto"></div><figcaption id=""><em id="">Radix Engine’s Enshrined Authorization and Royalties</em></figcaption></figure><h3 id="">Enshrined Transaction</h3><p id="">The correct interface between user and system is paramount for any system to be usable. And to be usable the interface must find the right balance between ease-of-use and power/flexibility.</p><p id="">In the Operating System world, the most common interface is the terminal, a user space process which gives a user a command line tool to call and compose various system calls.</p><p id="">In the DLT world, this interface is the transaction. The industry standard for a transaction is to use a single low-level, generic invocation call. Unfortunately this is too simple in that it makes it hard to understand what one is actually doing when interacting with the system.</p><p id="">Radix Engine, on the other hand, uses the traditional OS pattern and enshrines an <a id="" href="https://www.radixdlt.com/blog/radixs-asset-oriented-transactions">application language</a> (similar to a terminal scripting language such as bash) to call and compose system calls in a single transaction.</p><p id="">Because the entry point of a transaction operates in the application layer, implementing the language interpreter is done by adding a Transaction Processor native package.</p><figure id="" class="w-richtext-figure-type-image w-richtext-align-fullwidth" style="max-width:1087px" data-rt-type="image" data-rt-align="fullwidth" data-rt-max-width="1087px"><div id=""><img id="" alt="" src="/assets/66140bd186a38aa941b5c1d7_UrGwKDeh7iSIL_b9kS8FDGMuNwh4lpIdBpmku3Ofw5GzR5WsFctj1fI_U6jMXhZYpeQIKqCK0_KPAKoe3eL0_i4Tqs3Xlvt7-txmVf-oM9MLnWU8W29p5fKXAgCrKBlBQXcQZTC0Gj_MP8ZfTzzXpKc.png" width="auto" height="auto" loading="auto"></div><figcaption id=""><em id="">Radix Engine’s Enshrined Transaction</em></figcaption></figure><h3 id="">Enshrined BLS</h3><p id="">BLS signatures are an important crypto primitive as they allow for the possibility of threshold signatures. Unfortunately, running such logic in WASM quickly uses up the maximum cost unit amount. In the recent “Anemone” update, Radix enshrined BLS by executing it natively and found a 500x gain in performance when compared to WASM.</p><p id="">Because BLS logic is stateless, it is easily added as an additional precompile to the Scrypto WASM VM.</p><figure id="" class="w-richtext-figure-type-image w-richtext-align-fullwidth" style="max-width:1087px" data-rt-type="image" data-rt-align="fullwidth" data-rt-max-width="1087px"><div id=""><img id="" alt="" src="/assets/66140bd1097550ba82955589_SP-L6PiWCSLJc_CS4LGN08x1m8JteqeptDWhQMvsfhUATUY12SK49ePJDmCvgaJdgKGAfmQ2Z1_vXqMnc7j2mLcRVy4bpY5yuJstTQD9sN1hwbfbSDLXaKqGP5GyfF4h9q-Lq-EmE0nBA99LRjyhJQ.png" width="auto" height="auto" loading="auto"></div><figcaption id=""><em id="">Radix Engine’s Enshrined BLS</em></figcaption></figure><h2 id="">Conclusion</h2><p id="">What to enshrine and what not to enshrine is important for any DLT protocol. Unfortunately, the industry’s existing VM model makes every enshrinement decision a high stakes decision.</p><p id="">With the Operating System model as inspiration, Radix Engine solves this problem by adding a layer of indirection between “software” and “hardware”. This allows Radix Engine to express the notion of “enshrined software” and makes it easy for the protocol to add, modify and express new enshrined systems without making high stakes compromise decisions.</p><p id="">Originally the operating system was meant to be a small piece of software designed for the sole purpose of managing shared resources for multiple applications. As user demands for a better, faster, more secure platform grew, it has taken on more and more responsibility with a larger and larger suite of software.</p><p id="">DeFi will be no different.&nbsp; As demand for a faster, more secure, and more usable DeFi platform grows, increased enshrinement will follow. Radix Engine was designed with this in mind and provides the scalable and secure framework needed for expanding enshrinement into the future.</p><h2 id="">Articles in This Series</h2><p id=""><a href="https://www.radixdlt.com/blog/thoughts-on-suis-movevm">Article 1: Thoughts on Sui’s MoveVM</a><br><a href="https://www.radixdlt.com/blog/how-radix-engine-avoids-the-flaws-of-suis-movevm">Article 2: How Radix Engine Avoids the Flaws of Sui's MoveVM</a><br>Article 3: Radix Engine: A Better Model for “Enshrinement”</p>
