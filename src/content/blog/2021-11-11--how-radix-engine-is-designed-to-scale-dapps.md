<p id="">In an <a id="" href="https://www.radixdlt.com/post/radix-engine-v2-an-asset-oriented-smart-contract-environment">earlier article</a>, I described how Scrypto is only possible with the Radix Engine’s specialized application environment and its asset-oriented features. But Radix’s roadmap to unlimited scalability is also only possible through a tight integration between Radix Engine and <a id="" href="https://learn.radixdlt.com/article/what-is-cerberus">Cerberus</a>, Radix’s unique massively-sharded consensus system. That tight integration is what will make Radix not just scalable in special cases, but also finally allow a world of DeFi dApps to scale without limit.</p><h3 id=""><strong id="">The Foundation: Cerberus</strong></h3><p id="">Our <a id="" href="https://radixdlt.com/whitepapers/consensus">Cerberus whitepaper</a> describes our unique consensus algorithm that enables unlimited scalability (as is planned for integration into the Radix Public Network in the Xi’an release on our roadmap). The key to unlimited scalability is unlimited parallelism. Parallelism means that many things can be processed at the same time without slowing each other down.</p><p id="">Skipping over the details (which you can read in the <a id="" href="/assets/608811e3f5d21f235392fee1_Cerberus-Whitepaper-v1.01.pdf">whitepaper</a> or check out in our recent <a id="" href="https://www.radixdlt.com/post/cerberus-infographic-series-chapter-i">infographic series</a>), Cerberus in the end has these unique features that enable unlimited parallelism:</p><ol id=""><li id="">Provides a practically infinite set of shards that can come to consensus independently in parallel</li><li id="">Allows atomic consensus to be conducted (“braided”) across any set of shards for each transaction</li><li id="">Allows UTXO-like “substates” to be assigned to shards arbitrarily</li></ol><p id="">What’s a substate? A substate is just a little record of something where some particular rules had to be followed. For example, you might want a “token substate” type that records where some particular tokens are. One bit of token substate might say “these 5 XRD are in Bob’s account”. But the rules of token substates would require that, for that to be true, the transaction also had to include something like “these 5 XRD are <em id="">no longer</em> in Alice’s account”. That pair of substates would describe a send of 5 XRD from Alice to Bob, and the rules ensure that no XRD can ever be accidentally lost or created. We’ll talk more about why substates are important a little later.</p><p id="">Looking at these three features of Cerberus,&nbsp; you can imagine how Cerberus can allow an unlimited number of token transactions to be processed in parallel: The status of all tokens are assigned to substates <strong id="">(feature 3)</strong>. Tokens that are held by millions of different accounts can be scattered across a practically infinite set of shards <strong id="">(feature 1)</strong>. And when anybody wants to transfer some tokens, the specific shards that record the current ownership of those particular tokens can come to consensus <strong id="">(feature 2)</strong>.</p><h3 id=""><strong id="">Regular Smart Contracts Can’t Scale</strong></h3><p id="">However, to be a Layer-1 network for DeFi with full smart contract functionality, we need much more than just token transfers. We need <em id="">smart contracts,</em> and this means understanding the relationship between the consensus layer and the application layer.</p><p id="">The application layer is what defines what the network can do. On Bitcoin, the application layer is simply the rules of the BTC token; there is no smart contract functionality. On Ethereum, the application is the Ethereum Virtual Machine (EVM) where smart contracts run, allowing the rules of the network to be programmable. Most smart contract platforms follow something very similar to the EVM application layer.</p><p id="">In order to provide its three features for scalability through parallelism, Cerberus requires two key things from Radix’s application layer:</p><ul id=""><li id="">It must define the meaning and rules of the substates.</li><li id="">Each transaction must define which substates (and thus shards) must be included in consensus.</li></ul><p id="">The first is pretty obvious, and below we’ll see how Radix Engine uniquely defines substates for smart contracts in a very different way from Ethereum’s EVM.</p><p id="">The reason for the second requirement is more subtle. If a key part of parallelism is only conducting consensus across the shards that are <em id="">necessary</em> (Cerberus feature 2), then the application layer has to tell Cerberus <em id="">which shards are relevant</em> for each transaction. However, this is only possible with an application layer that knows what things are relevant – which substates matter to do what is desired.</p><p id="">The EVM is designed around the notion of <em id="">global ordering,</em> which means that absolutely everything that happens in the network is on a single timeline. This is necessary for the EVM because any transaction could make a change absolutely anywhere in the network (any smart contract); it’s impossible to predict. For this reason, the EVM cannot take advantage of Cerberus-style sharding and is fundamentally incompatible – at least if you want to take advantage of Cerberus’ scalability potential.</p><p id="">Radix Engine is instead designed around a notion of <em id="">partial ordering</em> where each transaction <em id="">must</em> specify the shards that will be included (although this doesn’t necessarily mean that the developer/app must specify it - as well see in a moment). This is a crucial feature to enable parallelism, but as we’ll see in a moment, it has to be done in the right way.</p><h3 id=""><strong id="">Radix Engine Parallelizes Smart Contracts</strong></h3><p id="">So the big question is this: If we want Radix to process transactions – ranging from simple tokens sends to complex multi-dApp DeFi interactions – how does Radix Engine define substates and how does it define what substates are <em id="">relevant</em> in a given transaction?</p><p id="">The answer is three key choices in how Radix Engine is designed:</p><p id=""><strong id="">1. Radix Engine treats tokens as global objects at the platform level. This is important to let us parallelize the movement of assets as much as possible.</strong></p><p id="">As discussed in previous articles, every DeFi application revolves around managing assets, and so Radix Engine makes assets a native feature of the platform as <em id="">resources</em>. Resources are the basis for tokens, coins, and even things like “badges” used for authorization.</p><p id="">This has <a id="" href="https://www.radixdlt.com/post/radix-engine-v2-an-asset-oriented-smart-contract-environment">enormous benefits for development</a>, but it also means that all assets can be freely scattered around substates and shards as needed. The typical EVM model only implements tokens through individual smart contracts, which causes an immediate bottleneck for sharding since all transactions involving a given type of token have to go through that single smart contract. Global resource-based token assets on Radix give us the flexibility we need.</p><p id=""><strong id="">2. Radix transactions are unique and based on “intent”. This is important to enable high throughput through dApps without conflicts.</strong></p><p id="">You might assume that, in the substate model, transactions would have to specify the substates (and thus shards) needed – as in our example above with the matched pair of substates that created a send of 5XRD from Alice to Bob. And in fact that <em id="">is</em> essentially how transactions work on a few UTXO-based networks like Bitcoin and Cardano.</p><p id="">However, this approach creates serious problems for smart contracts that process lots of transactions at the same time (ie. most of them). One transaction may be okay: my wallet can read the smart contract and determine, for example, which tokens should move in and out of it as a result and include all of those substates in the transaction. But think about <em id="">hundreds</em> or <em id="">thousands</em> of people using a DeFi smart contract like a Uniswap-like exchange dApp. My wallet might identify some tokens held by the smart contract that should come to me as a result of a swap and include those substates in the transaction (I don’t really care which tokens come out, but the transaction must identify specific ones). But by the time the transaction is submitted and processed, it becomes very likely that somebody <em id="">else’s</em> wallet identified the same tokens. Now suddenly my transaction is invalid and fails.</p><p id="">In fact, this is <a id="" href="https://twitter.com/sassal0x/status/1434114386931552256?s=19">exactly what happened</a> with the first DEX launched on Cardano. Many blamed this problem on Cardano’s “eUTXO” style state (which has some similarities to Radix’s “substates”), but really the issue wasn’t with eUTXO; it was the fact that <em id="">Cardano’s transactions specify the eUTXOs directly</em>, creating the problem that many transactions may specify <em id="">conflicting</em> eUTXOs.</p><p id="">Instead, transactions with Radix Engine specify <em id="">intent</em>. You can see what this looks like in my <a id="" href="https://www.radixdlt.com/post/scrypto-an-asset-oriented-smart-contract-language">previous article about Scrypto</a>. To use the DEX example, rather than the transaction saying…</p><p id="">“these <em id="">particular</em> tokens (eUTXOs) should be sent and received in the swap”</p><p id="">… a Radix transaction says…</p><p id="">“I want to send this <em id="">quantity</em> of tokens (I don’t care which ones) into the DEX, and I expect that I will receive a certain <em id="">quantity</em> of other tokens (I don’t care which ones) as a result.”</p><p id="">The specific substates don’t appear in the transaction submitted by the user. So how does Cerberus know which substates to use? Radix Engine itself determines them <em id="">at the time of execution</em> on the network.</p><p id="">So if my transaction says “I want to send 5 XRD”, Radix Engine can (deterministically) look at the token substates available and pick substates that represent <em id="">these particular 5 XRD</em> when the network actually processes the transaction. This means that the substates chosen are always good at that time, and conflicts between transactions are avoided.</p><p id="">(Note: Here I’m talking here about how transactions will operate once smart contract capability is added to the Radix network at the Babylon release and beyond, not the current Olympia release.)</p><p id=""><strong id="">3. Each smart contract (or “component” in Radix terms) – including all of its data and the resources it owns – is assigned to a single shard at any point in time. This is important to ensuring that each component can process as many transactions as possible.</strong></p><p id="">Typically the result of each execution of a smart contract (each time it’s run as part of a transaction) depends on the <em id="">previous</em> execution in some way. For example, a DEX swap changes the balance of tokens in its pool which in turn changes the exchange rate on the next transaction. This means that there’s not much reason to spread different parts of a smart contract across multiple shards (which means more complex consensus for each transaction).</p><p id="">Instead, the most efficient way is to run each component (a Radix Engine smart contract) – including all of its data and resources it owns – on <em id="">one shard</em>. Radix Engine does this by capturing the full status of each component within a single substate at any given time. Any resources that move into the component become part of that substate; and when resources move out of the component, they are split out of that substate (because remember, resources are global on Radix!).</p><p id="">As a result, each component on Radix has full use of its own shard that can run unimpeded by anything else going on on the network. On Radix, <a id="" href="https://www.radixdlt.com/post/scrypto-an-asset-oriented-smart-contract-language">user accounts are also components</a> and so each account also gets its own shard automatically.</p><p id="">(Note: Radix Engine actually lets us be a little more clever. We don’t have to exclusively assign one component to one shard, but it’s the simplest way to understand how Radix Engine can optimize per-component throughput.)</p><p id="">Going further, a given dApp might actually be made up of <em id="">multiple</em> logically modular components, each with its own shard. For example, a DEX dApp might include independent components for each “pair” so that trades on each pair can run independently without slowing each other. With Cerberus’ virtually infinite shardspace, this allows a dApps developer to essentially provision as much parallelism as they need for their own application – on top of the parallelism the network offers between separate dApps.</p><h3 id=""><strong id="">Putting It Together: Unlimited dApp Throughput</strong></h3><p id="">When talking about “scalability”, it’s easy to lose track of what’s important, particularly when it comes to the ability to scale an ecosystem of real DeFi dApps. Today on Ethereum, dApps may be composable, but throughput is extremely low because all transactions, including smart contract calls, go through a single global consensus process that is very slow.</p><figure id="" class="w-richtext-figure-type-image w-richtext-align-fullwidth" style="max-width:1063px" data-rt-type="image" data-rt-align="fullwidth" data-rt-max-width="1063px"><div id=""><img id="" src="/assets/618cd023f6b4af1996b6a9a7_TWh_NQ2TwixE4mWWG8RaDYvbzhkGM-599ytteecbaL0j-zXiumbrKPX7KP0ywqri8jgj8ZQxKQ4T098ac-743FBQvwbM0qixQg0SOjWJpc7GTuvD_hkMIrEBYY-iULn3qJmU2job.png" width="auto" height="auto" loading="auto"></div></figure><p id="">Most sharding concepts (such as Ethereum 2.0, Cosmos, and others) add a <em id="">limited</em> amount of parallelism through a fixed set of shards or side-chains. And still these architectures put a limit on how much throughput can be achieved on a given shard and for all of the dApps and tokens on that shard.</p><figure id=""
