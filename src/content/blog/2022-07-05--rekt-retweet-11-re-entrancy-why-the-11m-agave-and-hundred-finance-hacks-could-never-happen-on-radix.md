<p id="">TLDR: The EVM requires complex stacks of messages sent between contracts, including re-entering previously called contracts, allowing for exploits in the ordering of logic. On Radix, re-entrancy is disabled, and Scrypto provides protections that forces correct ordering.</p><figure id="" class="w-richtext-figure-type-image w-richtext-align-fullwidth" style="max-width:1600px" data-rt-type="image" data-rt-align="fullwidth" data-rt-max-width="1600px"><div id=""><img id="" src="/assets/62c4774d877c4b23c2350628_roQPfRbyd_0hsWIsCUDc6vZ5jDST8GLWQouueLoHIV1hbzfkJcgRVMCdLOiVayDYEFOul43nrSTIQCtxax1r4Em0etuZzUvHJDb0WgmwvFiShlCTKM5TkfnV0RPdOar-BpEA-0Zth5ZuD_kNUSg.png" width="auto" height="auto" loading="auto"></div><figcaption id=""><a id="" href="https://twitter.com/RektHQ/status/1503832693062213642">https://twitter.com/RektHQ/status/1503832693062213642</a></figcaption></figure><p id="">Agave DAO and Hundred Finance are forks of Aave and Compound, respectively, on the Gnosis (xDai) network. Like many “alt layer 1s”, Gnosis leverages the Ethereum Virtual Machine (EVM). These dApps allow users to lend tokens to receive interest, or borrow tokens and pay interest (fully backed by collateral).</p><p id=""> </p><p id="">To borrow, users first deposit collateral, such as Wrapped ETH ($wETH), into the dApp’s wETH account. With that collateral, tokens can be borrowed (such as the stablecoin $xDAI), so long as the value of the borrowed amount is lower than the collateral.</p><p id="">‍<br>To prevent the collateral being reused for more borrowing, the dApp records this in its “debt balance”.</p><figure id="" class="w-richtext-figure-type-image w-richtext-align-fullwidth" style="max-width:1200px" data-rt-type="image" data-rt-align="fullwidth" data-rt-max-width="1200px"><div id=""><img id="" src="/assets/62c4765992d18839de98f920_Agave-The-EVM-Way.png" width="auto" height="auto" loading="auto"></div></figure><p id="">On March 15, 2022, both Agave DAO and Hundred Finance were exploited within minutes.<br><br>For Agave, the hacker created their own custom smart contract, deposited collateral, borrowed funds, and re-entered the contract’s execution before it could update its debt balance.</p><figure id="" class="w-richtext-figure-type-image w-richtext-align-fullwidth" style="max-width:1200px" data-rt-type="image" data-rt-align="fullwidth" data-rt-max-width="1200px"><div id=""><img id="" src="/assets/62c4767a9cdfc1233d225fb6_Agave-The-Hack.png" width="auto" height="auto" loading="auto"></div></figure><p id="">This allowed the hacker to re-use the same collateral and borrow against it multiple times.</p><p id="">‍</p><p id=""><strong id="">The exploit boils down to three issues:</strong></p><p id="">1. The Agave contract did not follow the “checks-effects-interactions” pattern, as the borrowed funds were released prior to the debt balance being updated.</p><p id="">‍</p><p id="">2. The re-entrant call from XDAI back to the Hacker’s Contract was only possible because the XDAI contract allowed the “callAfterTransfer” function.</p><p id="">‍</p><p id="">3. And at the root of it all, re-entrancy is mandatory for the EVM to work because tx’s can only call a single smart contract. Functionality across contracts requires developers to string complex chains of calls to one another that sometimes re-enter previous contracts.</p><p id="">‍</p><p id="">But if contracts can be re-entered, exploits can happen if there is a single mistake in the ordering of logic, e.g. the check-effect pattern not being followed.</p><p id="">And it gets even more complicated when each and every token is its own smart contract, with its own logic that can contain mistakes, such as the xDAI token allowing callAfterTransfer.</p><p id="">‍</p><p id="">So how does developing in Scrypto on Radix’s upcoming Babylon release solve this?</p><p id="">‍</p><p id="">Re-entrancy is disabled, and the checks-effects-interactions pattern is enforced by Scrypto. </p><p id="">To use “Agave” on Radix, a user would construct a transaction that calls their own user account and the Agave smart contract component.&nbsp;</p><p id="">The transaction interacts directly with each component, specifying “physical” movements of tokens between vaults inside components.</p><figure id="" class="w-richtext-figure-type-image w-richtext-align-fullwidth" style="max-width:1200px" data-rt-type="image" data-rt-align="fullwidth" data-rt-max-width="1200px"><div id=""><img id="" src="/assets/62c6485cc50b251369aca196_Agave-The-Radix-Way.png" width="auto" height="auto" loading="auto"></div></figure><p id="">With the EVM requiring a chain of calls between contracts to update their internal lists of balances, re-entrancy is necessary if a callback is required.</p><p id="">‍</p><p id="">On Radix, each component interacts directly with the transaction. There is no chain of calls, so re-entrancy is disabled!</p><p id="">Furthermore Scrypto, Radix’s asset-oriented programming language, enforces the “checks-effects-interactions”pattern on developers, as “buckets” of tokens are returned only at the end of a function or method. Scrypto devs can’t make the mistake that led to this hack.</p><p id="">‍</p><figure id="" class="w-richtext-figure-type-image w-richtext-align-center" data-rt-type="image" data-rt-align="center"><div id=""><img id="" src="/assets/62c476e49fa02014abee38c0_image.png" width="auto" height="auto" loading="auto"></div></figure><p id="">If the hack were attempted on “Agave” on Radix, this would fail immediately, as re-entrancy is not possible, and the checks-effects-interactions pattern is enforced by Scrypto.</p><figure id="" class="w-richtext-figure-type-image w-richtext-align-fullwidth" style="max-width:1200px" data-rt-type="image" data-rt-align="fullwidth" data-rt-max-width="1200px"><div id=""><img id="" src="/assets/62c6486ac50b25949aaca839_Agave-The-Attempted-Hack.png" width="auto" height="auto" loading="auto"></div></figure><p id="">If you’d like to learn more about Scrypto, why not check out <a id="" href="https://docs.radixdlt.com/main/scrypto/introduction.html">our docs site</a> to get started:</p><p id="">‍</p><p id="">For the last in the Rekt Retweet series:</p><p id="">Rekt Retweet #10: Badges - <a id="" href="https://twitter.com/radixdlt/status/1541881913127960576">Why the $326m Wormhole hack on #Solana could NEVER happen on Radix</a></p>
