<p id="">‍</p><figure id="" class="w-richtext-figure-type-image w-richtext-align-center" data-rt-type="image" data-rt-align="center"><div id=""><img id="" src="/assets/62b2ffe5f1c388fc93daae20_image.png" width="auto" height="auto" loading="auto"></div></figure><p id="">‍</p><p id="">The incident in question, courtesy of <a id="" href="https://twitter.com/RektHQ/status/1366365255371210752">@RektHQ</a></p><p id="">TLDR: Ethereum relies on smart contracts sending chains of messages to one another. This brings complexity and sometimes chaos. Radix’s Transaction Manifest interacts with each component in turn, providing a simple, atomic, and composable way of guaranteeing token movements.</p><p id="">‍</p><p id="">Furucombo is a dApp on Ethereum that allows its users to combine multiple actions together in a single transaction, through an easy to use interface.</p><p id="">For example, users can arbitrage a price difference between two DEXs (although in the image below the user would lose money!).</p><figure id="" class="w-richtext-figure-type-image w-richtext-align-center" data-rt-type="image" data-rt-align="center"><div id=""><img id="" src="/assets/62b2e7110e4ff617ecc5e395_GrLNNzPzaudShaW7HOfrlJLmNkqe7jlvhtl-t3CeNw9ZaZdV-fQh_rV6rfJOnUkmTYu3PdPingpTtrgRWfwgYvE-ZWZllO5OAzD5LU4NMTYRgZ6bDJ15MePdECwti8IXLpQN0yX1woErGuglsg.png" width="auto" height="auto" loading="auto"></div></figure><p id="">‍</p><p id="">Furucombo exists because it’s not possible to call two or more contracts directly on Ethereum. Instead, you have to first deploy a custom smart contract that specifies what actions to take, and you then call that smart contract to execute those multiple actions. Ethereum also makes use of what are called “proxy” contracts. These act as a gateway, routing actions to other contracts depending on what needs doing.&nbsp;</p><p id="">‍</p><p id="">This is useful if a developer needs to deploy a new contract, as the proxy can be updated to route to the new contract.</p><figure id="" class="w-richtext-figure-type-image w-richtext-align-fullwidth" style="max-width:1200px" data-rt-type="image" data-rt-align="fullwidth" data-rt-max-width="1200px"><div id=""><img id="" src="/assets/62b2e736fe9f5662f628cd08_yxp9W4IRCOWhNOo-uhsr1ROci_Pg3sGY2JN7tze3fKt9CZbzVfThwgcu9l79i3xFr3wVS11GkK89GDabP7HlyGp8c-CWHjn1EMtEtCsvxPJ9GyJXxlx905lbhzVgIPZGMkBs8klgqO5tEkSgrw.png" width="auto" height="auto" loading="auto"></div></figure><p id="">Looking at the diagram above, you can see that Ethereum transactions are made up of long chains of messages sent from contract to contract.<br></p><p id="">When a contract sends an instruction downstream on behalf of an entity upstream, this is called a “delegate-call”.</p><p id="">‍</p><p id="">On Feb 27 2021, a hacker set up their own custom contract which instructed Furucombo to send a complex stack of “delegate-calls” to other contracts downstream.</p><p id="">One such delegate-call included the hacker’s own contract address, which Furucombo forwarded to an Aave Proxy. The Aave Proxy accepted the hacker’s address, and now routes messages from Furucombo to the hacker’s malicious contract.</p><figure id="" class="w-richtext-figure-type-image w-richtext-align-fullwidth" style="max-width:1200px" data-rt-type="image" data-rt-align="fullwidth" data-rt-max-width="1200px"><div id=""><img id="" src="/assets/62b2e79d47c02ff84a27c4c2_y7Urry-dL59Qmy9gmZqsV7wp9URjnL2xxry95CV-rOuiU02H0FAT_Sf-K5OF3XKqKSqVqvC8H0iKHkytiAc3_e92Z9bdDwkLgUJxMEzGpecHyMuHMOmRb2SYCt-cbpQF5o70V0XYceLWcLvdDg.png" width="auto" height="auto" loading="auto"></div></figure><p id="">With the Aave proxy pointing to the hacker’s contract, the hacker could now instruct Furucombo to use all its accumulated “approvals” across other ERC20 smart contracts (e.g. stETH, USDC, and Dai), and transfer those funds to the hacker. This drained $14m in total.</p><p id="">‍</p><p id="">So why could this hack never happen on Radix’s upcoming Babylon mainnet? Instead of chains of calls between contracts, transactions on Radix are composed using what’s called the transaction manifest. We’re going to dive into this in a bit more depth than in previous Rekt Retweets.</p><p id="">The first thing to note is that the transaction manifest describes all the asset movements that must happen between smart contracts that are part of that transaction.</p><p id="">So for the example arbitrage between two DEXs below, the transaction calls each component in turn with assets that “physically” move between the components, ultimately resulting in swapping between the two DEXs for a profit (or if not, then the transaction fails).</p><figure id="" class="w-richtext-figure-type-image w-richtext-align-fullwidth" style="max-width:1200px" data-rt-type="image" data-rt-align="fullwidth" data-rt-max-width="1200px"><div id=""><img id="" src="/assets/62b2e7d4d174310e9a429447_OHALs_xwzP4S67MqmA4qlJID-qiksWsEJoI8FPyy1sRCUr03txDHqh_XSMNKaZi1JP9EGr25NguTgpk1iCuc6BYoh4-ezbVyQEwzuaw0CdztTiWZJN2tT6AyqLVF-2XgK7B5E-lN3pwzIrtmHw.png" width="auto" height="auto" loading="auto"></div></figure><p id="">Compare this to Ethereum, where a transaction interacts only with the first smart contract, which sends messages downstream, and downstream again. This results in highly complex execution stacks and potential for error and exploitation. On Radix, as the transaction interacts with each component, components don’t even need to talk to each other to compose them together - the transaction itself can do it directly!</p><p id="">‍<br>This makes developing on Radix far more simple, as the transaction manifest speaks directly in a language of asset movement, and Radix Engine provides guarantees on how assets behave.</p><p id="">‍</p><p id="">Contrast this to a Solidity developer who has to account for a thousand and one ways in which their smart contract might interact with a complex stack of other third party contracts, invisible to the transaction that the user submits.</p><figure id="" class="w-richtext-figure-type-image w-richtext-align-fullwidth" style="max-width:1200px" data-rt-type="image" data-rt-align="fullwidth" data-rt-max-width="1200px"><div id=""><img id="" src="/assets/62b2e7fcfe9f56e2ca29270e_T891oThT-ED0zF0pBApSOufQyjTaxT9psI1cidUzNu7PKno8eh2kUS0EtkG_99kdV7-Y5aaFO_knqKzb9trPdEd3ShgxXuP9SMYgebkKu6YWLVEh_ABKpfMcBR8F1e4AvYFVUWj0A1_IpK3XKg.png" width="auto" height="auto" loading="auto"></div></figure><p id="">This also makes Radix components far more composable, as components are developed against standardized asset movements, just like a box of lego bricks is composable because the pins and holes are standardized.</p><p id="">‍</p><p id="">If the attack were attempted on Radix:</p><p id="">1. You would never need Furucombo on Radix, as the transaction manifest can compose with an unlimited number of components directly. There is no stack of calls from one contract to another for a hacker to exploit.</p><figure id="" class="w-richtext-figure-type-image w-richtext-align-fullwidth" style="max-width:1200px" data-rt-type="image" data-rt-align="fullwidth" data-rt-max-width="1200px"><div id=""><img id="" src="/assets/62b2e834a9afc87c550ecd94_GVbqR4d-SeFFCJPfCCbAGODZFFjxXhqnN9BMhXblDisjhmzb1Fr0ys4GfMwXv1Qi5YP7PuFBRt4OyV3eUO6uMoossFCdx65LYqxVIwXN7pduWXBVgyAQHZitPGBiEclNcUoen2ClYDugKQzXNg.png" width="auto" height="auto" loading="auto"></div></figure><p id="">2. As tokens are natively understood by the platform, and live in vaults inside components, there’s no more “approving” contracts to spend your tokens. “Draining” someone’s wallet using a hijacked approval just isn’t a thing on Radix.</p><p id="">‍</p><p id="">For a deep dive into the technicals of the Transaction Manifest, check out the relevant docs <a id="" href="https://docs-babylon.radixdlt.com/main/scrypto/transaction-manifest/intro.html">here</a>.</p><p id=""><br>For the last in the Rekt Retweet series: </p><p id="">Rekt Retweet #8: <a id="" href="https://twitter.com/radixdlt/status/1536777840359788544">Why the $90m Mirror Protocol hack could NEVER happen on Radix</a></p>
