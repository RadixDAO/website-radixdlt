<h2 id="">‍<strong id="">What is ERC-404?</strong></h2><p id="">A brand new experimental standard on Ethereum has emerged recently, generating a great deal of hype and excitement across many chains. This standard, named ERC-404, creates a sort of hybrid of other popular Ethereum standards, allowing for interesting things such as increased NFT liquidity and a form of fractional ownership.&nbsp;&nbsp;</p><p id="">Building towards these goals in the traditional Solidity way creates problems like unpredictable token behaviors and the need for integration with other dApps.&nbsp; The Radix and Scrypto approach solves all of the same problems ERC-404 aims to solve, but more intuitively, without the need for any new “standard”, and no need for integration with other dApps.</p><h2 id=""><strong id="">What does ERC-404 set out to achieve?&nbsp;</strong></h2><p id="">ERC (Ethereum Request for Comment) is a process used on Ethereum to propose and agree to new smart contract standards.&nbsp; The most popular ERC standards are ERC-20 and ERC-721, which are the most popular implementations of fungible and nonfungible tokens, respectively, on the Ethereum ledger.&nbsp;&nbsp;</p><p id="">Fungible tokens are tokens that are identical and mutually interchangeable, such as Bitcoin.&nbsp; Nonfungible tokens (NFTs) are unique tokens that cannot be subdivided.&nbsp; The creation of ERC-404 blurs the lines between both fungible and nonfungible tokens.</p><p id="">The two main goals of this new standard are:<br></p><ol id=""><li id="">Allowing a non-fungible collection to have access to fungible liquidity&nbsp;</li><li id="">Allowing for fractional ownership of an NFT in a collection<br>‍</li></ol><p id="">These goals create excitement because NFTs are traditionally illiquid assets in nature, and some collections can be so expensive that the price of a single token can exclude a large portion of the market.&nbsp; Pandora was among the first projects to implement ERC-404, creating a collection of 10,000 tokens that can be minted into NFTs with five different rarities.&nbsp; Allowing an NFT collection to have a portion of its supply added to a DEX like Uniswap also helps set and maintain a floor price for the collection, which is a benefit in itself.&nbsp; Owning a part of a Pandora fungible token allows you to own a fraction of one of these NFTs.</p><p id="">These goals are great to have and I think are useful to create more interesting NFT use cases; however, the way this idea is implemented with the ERC standard creates confusion and inefficiency when it doesn't have to.</p><h2 id=""><strong id="">Problems with ERC-404 on Ethereum</strong></h2><p id="">The initial version of this standard created a situation where if a user owned a single ERC-404 token, it existed as both a fungible token and an NFT in the user's wallet at the same time.&nbsp; This also came with an invisible mapping of these fungibles to the non-fungibles in the user's account.&nbsp;</p><p id="">If an ERC-404 fungible token is sent to another address, swapped on a DEX, or the total balance is otherwise reduced below a whole token, an NFT in that account would suddenly be burned.&nbsp; If you happen to have multiple NFTs, you could end up losing one that you would prefer to keep!&nbsp;&nbsp;</p><p id="">ERC-404 users would need to split tokens to different wallets as well as be very careful about moving any fungibles in order to keep any rare NFTs safe from being burned accidentally.&nbsp; This sort of extra headache renders the early version of ERC-404 not very useful because no serious fintech products would accept this level of unpredictability and risk of loss for their customers.&nbsp; If there is potential to use ideas from ERC-404 for things such as RWA, users need a reliable and intuitive experience using the tokens.</p><p id="">When ERC-404 was first released, NFT marketplaces did not innately understand what these 404 tokens were or how to deal with them.&nbsp; Blur was very quick to integrate the standard, but is it good to require another dApp to perform work to make sure the platform is compatible to work with your new token or dApp idea?&nbsp; This inefficiency is due to all dApp logic being crammed in with the code that also defines what the token is and can even do.&nbsp;&nbsp;<strong id="">‍</strong></p><h2 id=""><strong id="">Solving the Problem in a Better Way</strong><br></h2><p id="">With Scrypto, all of your dApp logic is entirely separate from the logic defining token behaviors so this is never the case.&nbsp; If a builder innovates an interesting new idea, it is already guaranteed to integrate with the rest of the dApps on ledger without any sort of ERC process.</p><p id="">Building the “Ice token” with Scrypto allowed me an opportunity to approach the problems of NFT liquidity and fractionalized ownership from a different perspective.&nbsp; When building a dApp on Radix, developers don’t need to write code to define what a token is and what physics this token is allowed to have because Radix’s platform native “resources” already include that. Instead, developers can write logic purely dealing with manipulating these predictable assets with dApp-specific logic outside of the resource itself.</p><p id="">The question I kept asking myself while researching ERC-404:&nbsp; Why not just make distinct fungible and nonfungible states for the tokens and create a simple smart contract that will facilitate an easy transition between these states that a user can call when it is convenient for them?&nbsp;</p><p id="">Using Scrypto, it is straightforward to create a fungible and a nonfungible resource and write logic that caps their combined supply to whatever number is needed.&nbsp; By linking these two different resources in a 1:1 relationship, the dApp takes in a number of tokens and mints and returns only the exact same amount back to the user thus ensuring no deviation from maximum supply.&nbsp;&nbsp;</p><p id="">There is no longer any need to possess these tokens at the same time which removes a lot of headache. Instead of a smart contract triggering strange behaviors when a user decides to use tokens they should rightfully own, users only need to worry about converting tokens between states when interacting with the specific smart contract built for that task.</p><p id="">Using Scrypto, I decided to try to solve the goals of ERC-404 differently, which I call an “Ice token.” With this method of solving the application problem on Radix, users can do whatever they wish with their NFTs.&nbsp; Send them, trade them, list them all with no issues or the need to "dynamically mint" fungibles in different places.&nbsp; Likewise, users can do whatever they wish with their fungibles.&nbsp; Send them, trade them, add them as liquidity without fear of losing any NFTs.</p><p id="">This approach also makes fractional ownership of NFTs quite easy.&nbsp; Converting fungibles to NFTs requires a whole fungible token.&nbsp; If a user decides to convert 1.5 fungibles to NFTs, they will receive 1 NFT and .5 fungible tokens change.&nbsp; Converting NFTs back into fungible tokens always results in a whole number of fungibles.</p><p id="">An added benefit is that none of this requires a “new standard” on Radix at all. The ice token is really just a pattern of building a dApp that uses the tools that Radix provides and will work “out of the box” without the ecosystem having to agree to new special treatment, like ERC-404.</p><p id="">Ice token happens to have slightly different logic than Pandora's for minting. Ice minting logic is set to maintain constant percentages of rarity for each possible metadata. This could easily have used the same methods that Pandora used. The point is that any desired business logic can be inserted to manage minting and manipulation of these non-fungible and fungible tokens.</p><p id="">I think once this newer more intuitive and asset oriented paradigm of building reaches the masses, it will be quite obvious that standardizing behaviors at the resource level is the correct design choice for building smart contracts for many reasons including safety and compatibility.&nbsp; This is just the beginning of the NFT tech on Radix expanding and working towards building things that are only possible on the Radix ledger.</p><p id="">Ice component repo: <a href="https://github.com/aus87/ice_rrc404v1">https://github.com/aus87/ice_rrc404v1</a></p>
