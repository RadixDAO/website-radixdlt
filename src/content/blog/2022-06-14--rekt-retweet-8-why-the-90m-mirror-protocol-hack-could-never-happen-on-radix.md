<p id="">TLDR: COSMWASM developers must implement validations to prevent funds being withdrawn multiple times. On Radix, as tokens and badges provide native ways to account for user positions and authorize actions, a Radix dApp would never be designed with a vulnerability like this.</p><figure id="" class="w-richtext-figure-type-image w-richtext-align-fullwidth" style="max-width:1478px" data-rt-type="image" data-rt-align="fullwidth" data-rt-max-width="1478px"><div id=""><img id="" src="/assets/62a8c8ae50ef650ac9296d82_i34b-9ipotAAM9TkuAan4k_109rdZCpaWEimcof0HugkKBBUGDvIQb2Mi1tD2jU1fYxmetKpq7iqAf9SZwvTqGMuju7jJBgOKwqjIgszAEfUrQlytHnW6Hn5mLVT4PQ0kCRd0aEnkkNo7t6MvA.png" width="auto" height="auto" loading="auto"></div><figcaption id="">The incident in question <a id="" href="https://twitter.com/RektHQ/status/1531703993109561345">https://twitter.com/RektHQ/status/1531703993109561345</a></figcaption></figure><p id="">Mirror Protocol was a dApp on Terra (now Terra Classic) that allowed users to deposit collateral, such as UST, and mint “mAssets”, which are synthetic tokens that mirror the price of another asset such as ETH (the mirrored version would be mETH).<br><br>Other users are able to open long or short positions against those mAssets by depositing collateral and buying or selling short those mAssets. Depending on how the price of the mAsset changes, those users can then close those positions for profit or loss, or get liquidated.</p><p id="">To close a position, a user submits a tx to the Mirror contract. Their account is linked to a Position ID with metadata recording the user’s collateral, leverage, and position. As this position is in profit, when closed, the user is credited the collateral and position.</p><figure id="" class="w-richtext-figure-type-image w-richtext-align-fullwidth" style="max-width:1200px" data-rt-type="image" data-rt-align="fullwidth" data-rt-max-width="1200px"><div id=""><img id="" src="/assets/62a8c8ea650c36e8d38fb4ac_D_78mX71xnoPcgKXPftZThZB82cU0m1xXKyOvGhOyd5EXJFLGkn80rGxZgoDuz64wcAgOpagWdcAvoCF8qagc9yraPwSL5kQDJ441YQVPFWSFhdAs5zEm-A9JjtqVosJKXJbrQFBQBBMD5h6rA.png" width="auto" height="auto" loading="auto"></div></figure><p id="">On Sep 11 2021, a hacker was able to trick the Mirror contract into closing an inflated position multiple times as the contract did not check for duplicate withdrawals. For one transaction, the hacker used the same position (43186) to withdraw ~100k UST 437 times.</p><figure id="" class="w-richtext-figure-type-image w-richtext-align-fullwidth" style="max-width:1200px" data-rt-type="image" data-rt-align="fullwidth" data-rt-max-width="1200px"><div id=""><img id="" src="/assets/62a8c9e7b8dca1144bcafe91_rgD5vx3fDYAovGV4KrKC3nIoZajYSmixaYCp-MYyxmp-Mo12_hukRYSL6Rf-XKBhmtehik7oallAC2SIDIgEp7Zv9nfVI724dQ2bmZLDYR2pvL0JfHuGAimiwb_TkHmw-8bhQTEs6bnghfLoQA.png" width="auto" height="auto" loading="auto"></div></figure><p id="">So why couldn’t this hack happen on Radix’s upcoming Babylon mainnet?(1) To authorize the closure of a position, the user would have to present a “badge” (a resource like an NFT) that is associated with their position. Once the position is closed, the badge is burnt.</p><figure id="" class="w-richtext-figure-type-image w-richtext-align-fullwidth" style="max-width:1200px" data-rt-type="image" data-rt-align="fullwidth" data-rt-max-width="1200px"><div id=""><img id="" src="/assets/62a8ca027b4021c088ef4e64_fcm5WefBs6YrG0acilJWoW0bx_t8T7chpiMwCdmkP9aVZ2j24FR0FUw4qi97gdzzL8RShNyV_Q5NFwnqbuMRAA5VHfFhmoD4_tOPOlCj9Xzo486s6oAZx23BJlENfsX7S62zSyPkwDuRfKa74g.png" width="auto" height="auto" loading="auto"></div></figure><p id="">‍</p><p id="">(2) Tokens on Radix live in vaults inside components (smart contracts). For “Mirror” on Radix,<em id=""> each position</em> would have its own vault. This means that once the position is closed, the vault for that position is empty!&nbsp;</p><p id="">This means there’s no more pooling of user funds into “omnibus” accounts, where if there’s an error in accounting, the entire pool - and everyone’s tokens - can be drained. Instead, individual vaults for each position make Radix dApps far more safe and intuitive to build.<br>‍<br>Now back to the hack, which fails immediately as the badge for the position is burnt after the first withdrawal, and the vault is then empty!<br><br>As the tokens live in a specific vault for each position, there is no scope for the developer to miss a “duplicate withdrawal” check.</p><figure id="" class="w-richtext-figure-type-image w-richtext-align-fullwidth" style="max-width:1200px" data-rt-type="image" data-rt-align="fullwidth" data-rt-max-width="1200px"><div id=""><img id="" src="/assets/62a8ca29e72f3b10dca1940b_xXJ7atm-zhflacoHFa0sd7U8lr80eznIB_108cko1v8yM2ydV0oOPwPOaN36bt1Y6Bz55f9ZR8K6FRG66Qbfc6INgzisBkVs-ze_DRuEPkz6G7CMZNX0qnK_8rvTGDADf4I1TU1saKISya0OjQ.png" width="auto" height="auto" loading="auto"></div></figure><p id="">If you’d like to learn more about how Scrypto is a game changer for DeFi, I recommend you read this article on Scrypto <a id="" href="https://www.radixdlt.com/post/radix-engine-v2-an-asset-oriented-smart-contract-environment">https://www.radixdlt.com/post/radix-engine-v2-an-asset-oriented-smart-contract-environment</a></p><p id="">For the last in the Rekt Retweet series:</p><p id="">Rekt Retweet #7: <a id="" href="https://twitter.com/radixdlt/status/1534185897830359045">Why #Radix Blueprints and Components would have prevented the $11m Value #DeFi hack on $BSC</a></p>
