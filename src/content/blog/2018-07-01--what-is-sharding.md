<p id="">Put simply, <strong id="">sharding</strong> is breaking a single database into smaller, more manageable chunks, and distributing those chunks across multiple servers, in order to <strong id="">spread the load</strong> and <strong id="">maintain a high throughput</strong>.There are two main ways of cutting up a database - vertical partitioning and horizontal partitioning.</p><figure id="" class="w-richtext-figure-type-image w-richtext-align-center" data-rt-type="image" data-rt-align="center"><div id=""><img id="" src="/assets/6087c86f8d67506fbef2f9bd_et25j2xD2OEC5u1MbooaV39vEjTa656ahq1LxZ-U1OGfE8i1sZWRrsamoW-RxguIMMCU6EqS0Hw9eKio0mZe_Qa0L8MN0qzbI7a1q_3Utu0CYqcqGNT1dsJItwiE7kFDq2rK8tTS.jpeg" width="auto" height="auto" loading="auto"></div></figure><p id=""><strong id="">Vertical partitioning</strong> happens when different tables from the same database are stored in different instances. Each table is a distinct shard. A simple example of this would be putting all the transactions from North America in one table, and all the transactions from Europe in another table.</p><figure id="" class="w-richtext-figure-type-image w-richtext-align-center" data-rt-type="image" data-rt-align="center"><div id=""><img id="" src="/assets/6087c86fc119d6ca7e09b9b4_XuyvveVpWGOZFP34tpYwe3VHssGafkGRhjUFQU2PFp-RtH8JPO-AWHlV9SbNwBqngXiRfNzMdcsx-I3ApGfa8agZ96X2vhxZ08JOE2qlQG876ZnBzGHnDgIOiGn4pLGPdKfO96.jpeg" width="auto" height="auto" loading="auto"></div></figure><p id=""><strong id="">Horizontal Partitioning</strong> splits the database table into separate sets of rows, and these rows are stored in different database instances. Each set of rows is a shard. A simple example of this would be ‘“Server 1’” taking rows 1 to 10,000 and “Server 2” taking rows 10,001 to 20,000, and so on.Horizontal partitioning has has two advantages over vertical partitioning:</p><ol id=""> 	<li id="">You do not need to plan how to split your data up in advance;</li> 	<li id="">Your database isn much less ‘“lumpy’” - you can dynamically scale how much of the whole database any one server needs to service.</li></ol><h2 id="">Why is Sharding Important?</h2><p id="">If a server cannot handle the requested number of operations, you can split that data set into parts that can be stored on different hosts.For example, if we split a single table into two partitions, then each host will need to handle <em id="">half</em> of the operations &nbsp;of the original host. As the operation requests increase, the database can be split into more and more parts.</p><figure id="" class="w-richtext-figure-type-image w-richtext-align-center" data-rt-type="image" data-rt-align="center"><div id=""><img id="" src="/assets/6087c86f0ab31f9bc891145c_l37_2iymfINsqrfm-H4tMzj7-2zOVPQUDaMlPPwzP_dGotfVArwa74jrWRAy7EWvBM6FSUlADmNUeZlzC3wqNEQ571GVp4wV_hP4-oW9RWnqwgyjLy7mMMrT2RfRO0bumfqzwXO.jpeg" width="auto" height="auto" loading="auto"></div></figure><p id="">Sharding is a well established scaling solution for systems with large data sets and/or high throughput operations.</p><h2 id="">What is Distributed Ledger Technology (DLT)?</h2><p id="">A <strong id="">Distributed Ledger</strong> is a database that is replicated, shared and synchronized across multiple sites, countries, and institutions. A DLT contains a <strong id="">consensus algorithm</strong> -- a mechanism for agreeing between the parties on what the most up to date version of the ledger should be, and for resolving faults, errors or conflicts.</p><figure id="" class="w-richtext-figure-type-image w-richtext-align-center" data-rt-type="image" data-rt-align="center"><div id=""><img id="" src="/assets/6087c86fa74dfafa19a2de30_wHSaOh7gNMhreIJo_-PPofvI1dVNlPQmtsSyWhdaqrPQgVgDWtmWcJnxIaZHC-gRtVv8YdNC394XJ9stWtXaZ4DvJpSArc5AHxKW7RAsS4MoBreDEkUFEpxQ86Gf59zuTJLUk9kF.jpeg" width="auto" height="auto" loading="auto"></div></figure><p id="">DLT networks are <strong id="">peer-to-peer</strong>, meaning there is neither a centralized administrator function nor a centralized data store. Public blockchains such as Bitcoin and Ethereum are, perhaps, the best-known examples of DLTs.</p><figure id="" class="w-richtext-figure-type-image w-richtext-align-center" data-rt-type="image" data-rt-align="center"><div id=""><img id="" src="/assets/6087c86f553bd01013cd28f7_boZ2tPfUVdY2Paw_7Na5nGx1gOYSVL7oOQE95sLMVJX52Qsgc0BjyZKz3-_kGy8ANOYymgwgCHh36fL9Yo10lK97YWvSBzpjuUq0wVkO9k0dYinKfYcjiu7uyAKdM2-DhVoQs0mO.jpeg" width="auto" height="auto" loading="auto"></div></figure><p id="">DLTs require independent machines, or <strong id="">nodes</strong>, to record, synchronize and share transactions in their respective ledgers.Distributed ledgers can be <strong id="">permissioned</strong> or <strong id="">permissionless</strong> depending on whether or not nodes require permission to change the ledger. Ledgers are <strong id="">public</strong> or <strong id="">private</strong> depending on whether anyone (as opposed to just nodes in the network) can access the ledger.</p><figure id="" class="w-richtext-figure-type-image w-richtext-align-center" data-rt-type="image" data-rt-align="center"><div id=""><img id="" src="/assets/6087c86fb2aec0cdd73646fd_CcV6I2kjCNbEqaNP-l7E1Vk-MhANMuImPDd2ansdnLLnozcphEh0kqrAF5K-P9l5mSVlxdCMBmVDocfgFUY0CClkqfjfiFIhvTAz-mr-vUmhhMJNVEDqzNA4297gMxYzFZCNhiC1.jpeg" width="auto" height="auto" loading="auto"></div></figure><h2 id="">What are DLTs used for?</h2><p id="">DLTs can be used for creating the following:</p><ul id=""> 	<li id="">digital currencies;</li> 	<li id="">digitally unique objects;</li> 	<li id="">digital objects with intrinsic value (like tickets).</li></ul><p id="">We can extrapolate many related use-cases from these, including cryptocurrency, notary services, prediction markets, smart contracts, audit trails, regulatory reporting, streamlining clearing and settlement, digital identity, and so forth. And that’s just the beginning.</p><p id="">Basically, distributed ledgers can be used in some form wherever securing digital relationships via a system of record is required, and control of a central authority is not desired. </p><p id="">In other words, DLTs are useful where there is a need for a trustless, peer-to-peer network for exchange of incentives and value.</p><h2 id="">How does sharding a DLT introduce the potential for fraud?</h2><p id="">To understand a distributed ledger is to grasp the notion of ‘“spend’”: that which is <em id="">spent </em>on one place in the network is <em id="">gained</em> somewhere else. Sharding a public DLT is difficult because you must be able to ensure that a spend has happened <em id="">only once</em> on the entire network. This is already tricky <em id="">without</em> sharding, and having multiple shards makes this even more difficult.</p><p id="">If a transaction that should happen only once is recorded across an entire network as happening <em id="">more than once</em>, then you run into a situation known as a <strong id="">double spend.</strong></p><p id=""><strong id="">‍</strong>Consider this: by splitting up a DLT into multiple shards, it is possible for a bad actor to take over a small part of the network with fewer computing resources. &nbsp;For example, if you divide a DLT into two shards, with half of your nodes working on one shard and half on another, you now need only 25% of the hash power of the network to attack one of the two shards. &nbsp;With enough nodes reflecting this false spend, a double spend is now possible.</p><p id="">When a double spend is possible on a DLT, it allows a <a id="" href="https://en.bitcoin.it/wiki/Irreversible_Transactions">form of fraud</a>. In late May of 2018, a <a id="" href="https://www.ccn.com/bitcoin-gold-hit-by-double-spend-attack-exchanges-lose-millions/">double spend attack</a> was launched against the Bitcoin Gold exchange: in this attack, a bad actor was able to <a id="" href="https://en.bitcoin.it/wiki/Majority_attack">acquire over 50%</a> of the network’s total hashpower. By doing so, they were able to modify and omit transactions of their own coins from blocks. &nbsp;Subsequently, they could reverse transactions that were previously confirmed.</p><figure id="" class="w-richtext-figure-type-image w-richtext-align-center" data-rt-type="image" data-rt-align="center"><div id=""><img id="" src="/assets/6087c86f79ff7105f31a7fff_EJdVJUW1hkKsRWhKSvyJPXcmqm89O1Zb4VytQ7t3as0BATgbvb1USHY38XqbnCsNzdvEJXCcXT28fDBpY9trIw5ERo4MABiJt4aDgToQNjIDJUVF_JYtXk9IYE_51qe5Drg1ylaS.jpeg" width="auto" height="auto" loading="auto"></div></figure><p id="">Understanding how a double spend works reminds us how &nbsp;a sharding a DLT introduces this potential for fraud: ledgers are a transaction record, and they exist to make sure that each spend happens only once. In a <em id="">distributed</em> ledger, the shards that form the ledger are not all in the same place, and thus are not going to be <a id="" href="https://en.wikipedia.org/wiki/Strong_consistency">immediately consistent</a>.</p><h2 id="">Conclusion</h2><p id="">These problems illustrate ways in which sharding a distributed ledger is difficult: ledgers are a transaction record, and they exist to make sure that each spend happens only once. In a distributed ledger, the shards that form the ledger are not all in the same place. According to the <a id="" href="https://en.wikipedia.org/wiki/CAP_theorem">CAP theorem</a> of distributed databases, a distributed data store (or ledger, in our case) cannot simultaneously provide more than two out of the following three guarantees: Consistency, Availability or Partition tolerance.</p><p id="">Put more simply, you need to make sure a spend has happened only once on the entire network, and having a lot of shards makes this difficult.In the next article, we’ll review how a 51% attack presents specific problems when sharding a blockchain.</p><p id="">Stay tuned for more on these specific problems, especially sharding, some attack tools and vectors, and how they are solved in Radix DLT.</p>
