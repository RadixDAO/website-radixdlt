<p id="">Scrypto v0.4 is here, bringing with it our first public test environment for Babylon, a primitive sneak peek of how a website can interact with an on-ledger application, and a shiny new authorization model.&nbsp; There’s a lot to cover, so let’s jump right in.</p><h4 id="">Enabling web frontends</h4><p id="">Ever since the release of Alexandria, the most commonly asked question by devs has been “How can I connect a website to my Scrypto component?”&nbsp; With the release of v0.4, we finally have an answer.&nbsp; It’s rather coarse, employing placeholder versions of tools and libraries which will be greatly improved in the future, but it works!</p><p id="">The system looks something like this:</p><ul id=""><li id="">We host a public test environment which runs a copy of the Radix engine simulator and a filesystem-based ledger.&nbsp; It’s not a network, and there’s no consensus process running.</li><li id="">The public test environment exposes a REST API which allows developers to publish code, submit transactions, and perform read requests about ledger state.</li><li id="">We offer a Chrome browser extension which behaves like the most basic imaginable wallet.&nbsp; It can sign transactions and submit them to the test environment.</li><li id="">We offer a JavaScript SDK which can assemble transactions and knows how to talk to the browser extension and the REST API.</li><li id="">Website developers can import the JavaScript SDK and use it to establish a connection to the browser extension as well as the public test environment.&nbsp; They can query for information like account balances, build up a transaction from user intent, pass that transaction to the browser extension for signature and submission, and then receive back a result of what happened.</li></ul><p id="">‍</p><p id="">The end-user experience is a far cry from what you can expect later this year, but it gives devs the ability to experiment with building out a critical piece of their dApp - the user interface.&nbsp; It’s also the first opportunity to compose transactions involving components written and deployed by multiple different people to a shared environment.</p><p id="">With this release, it’s finally possible for devs to come together to build and test the first “mini DeFi ecosystem” on Radix.&nbsp; Who will be the first?</p><h4 id="">Solving authorization the right way</h4><p id="">Safe, powerful, and easy-to-use authorization is foundational to the success of DeFi, Radix, and Scrypto, and we knew that we needed a greatly improved model from what we initially released in December.</p><p id="">Our biggest design challenge was creating a system that “gets out of the way” so you barely have to think about it 95% of the time, while still allowing complete flexibility for unusual scenarios that require highly complex rulesets.</p><p id="">After months of thinking, tinkering, and listening to feedback from our developer community, we have finally cracked the problem and are releasing the new model.&nbsp; We can’t wait to see what the creative minds of our community will do with it.</p><h4 id="">Introducing unified system-level authorization</h4><p id="">There are two primary use cases which require robust access control: guarding access to a component method call (e.g., only the owner of this account should be able to withdraw tokens from it), and restricting who is able to manipulate resources in various ways (e.g., minting, burning, changing metadata).&nbsp; In Scrypto v0.4, the system inherently understands both of these needs, and can “just take care of it” without the user or developer having to be explicit about authorizing these actions each time.</p><p id="">How does it work?&nbsp; For a particular action (whether method call, or resource action), a developer can set the rules that govern when it is permitted. For example, you might want to specify that “2 of these 3 badges must be present in order to mint more of this token.”&nbsp; When creating a transaction, required badges can be fetched from wherever they are located (maybe one is in a user’s account, and another is held in some other shared component which in turn needs a different badge to retrieve it), and they are automatically placed in something we call the <strong id="">authorization zone</strong> of the <a id="" href="https://www.radixdlt.com/post/scrypto-v0-3-released">transaction worktop</a>.</p><p id="">During a component call from a transaction, the system is always aware of the contents of the authorization zone.&nbsp; If a called component wants to mint more of a token, it doesn’t have to explicitly specify any badges to do so; it can just attempt the mint action, and the system will determine if the minting rules can be satisfied by the collection of badges present in the authorization zone.</p><p id="">This exact same kind of logic, and same method of specifying the rules, also applies for restricting access to component methods.&nbsp; If your gumball machine only allows holders of an admin badge to call a <strong id="">collect_coins</strong> method to pull the collected money out, that restriction is understood by the system, and callers do not have to explicitly pass in the badge.&nbsp; If the appropriate admin badge is present in the authorization zone, the call is permitted.&nbsp; If the badge isn’t present, the system instantly aborts the entire transaction.&nbsp; Easy peasy.</p><h4 id="">What are the benefits of the new model?</h4><p id="">There are a few big ones!</p><p id="">First and foremost, it allows us to expose the rules to off-ledger tools like wallets in a standard way which they can comprehend.&nbsp; This enables clear communication to the user on the rules governing methods and resources, and permits clever wallets (like <a id="" href="https://www.radixdlt.com/post/rdx-works-wallet-roadmap">the one we’ll release</a>!) to intrinsically understand whether the user can produce the necessary badges for access, and even present those badges in the transaction automatically.</p><p id="">Second, it’s just easier from a code perspective to not have to be fiddling with the badges directly when doing privileged actions.&nbsp; You don’t need anything passed in.&nbsp; You don’t need to specify what is permitting you to perform an action.&nbsp; You just <em id="">attempt the action</em>, and it succeeds or aborts as appropriate.&nbsp; It’s actually harder to explain than it is to use; in practice, it’s all magically delicious.</p><p id="">Finally, this approach means that we can also enable modification of the rules when instantiating a component from a blueprint. Want to use the Radiswap blueprint but have <em id="">your</em> component restrict the <strong id="">swap</strong> method to holders of your membership badge?&nbsp; No problem.</p><p id="">It’s important to point out that we haven’t lost the primary advantage of our original authorization model: the whole system functions entirely without the need for a concept of “who is calling me.”&nbsp; The design pattern of access control based upon knowledge of your caller is all but universal in the DLT space, and it’s not a good pattern!&nbsp; It puts too great a burden on the developer to get it <em id="">exactly</em> right in a complex system of interoperable smart contracts, and it has led to the loss of hundreds of millions of dollars.&nbsp; Once a developer gets their first taste of badge-based authorization with Scrypto, there’s no going back.</p><h4 id="">Details, details, details</h4><p id="">Want concrete examples?&nbsp; Wondering how we prevent authorizing things you didn’t intend?&nbsp; Curious about how to handle complicated rulesets that require things like branching logic?&nbsp; There’s a lot of detail we didn’t cover in this summary, so please see the <a id="" href="https://docs.radixdlt.com/main/scrypto/scrypto-lang/access-control/access-introduction.html">related documentation</a> for the good stuff.</p><p id="">Authorization isn’t the only big change to Scrypto that came with v0.4!&nbsp; Please see the <a id="" href="https://docs.radixdlt.com/main/scrypto/release_notes/v0_4.html">full release notes</a> if you’re an existing Scrypto developer and want to know why your code suddenly stopped compiling.</p>
