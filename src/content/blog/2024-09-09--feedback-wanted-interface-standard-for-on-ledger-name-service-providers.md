<p id="">The topic for this <a id="" href="https://www.radixdlt.com/blog/feedback-wanted-introduction">call for feedback</a> is a flexible and narrowly-defined interface standard for generalized <strong id="">“Name Services” on Radix</strong>.</p><h2 id=""><strong id="">Introduction</strong></h2><p id="">Systems like Ethereum’s “ENS” (Ethereum Name Service) have shown that it is useful and desirable to have a standardized way for blockchain accounts to have human-readable names assigned to them that can be used in place of unwieldy addresses.</p><p id="">The most flexible and open way to support such services is to agree on a standard interface on Radix that will allow both component logic and clients – notably the Radix Wallet – to use any “name service” the user desires to automatically look up and discover names assigned to accounts, without special app-specific integrations.</p><p id=""><strong id="">This is a proposal for a flexible and narrowly-defined interface standard for generalized “Name Services” on Radix</strong>. The proposed standard does not seek to constrain the internal functioning of such services, nor constrain the specific features that they may offer. For example, this interface proposal is agnostic to things like namespacing, and methods of name ownership and management.</p><p id="">The intention is to seek community feedback toward swift agreement on a standard that would enable the Radix Wallet, and other clients and libraries, to implement it. This would allow developers to create a wide variety of name/alias/domain services that comply with this standard and have <strong id="">instant discovery and lookup support in the Radix Wallet</strong>, letting users conveniently make use of names in place of complex account addresses.</p><p id="">Thanks to the XRD.Domains team, who provided much practical and helpful product requirement input that went into this proposal.</p><p id="">‍</p><h2 id=""><strong id="">Goals for the Name Service Interface Standard</strong></h2><ul id=""><li id="">Allow both client software and on-ledger components to “know” how to do name lookups on any Name Service, given only an address for a Name Service Provider component that implements the interface standard.</li><li id="">Allow association of arbitrary name strings to account addresses.some text<ul id=""><li id="">Each name can only point to one account, so a given name may be used directly in place of an account address without disambiguation.</li><li id="">Multiple names can point to one account.</li><li id="">Names offered by different Name Services can point to one account.</li><li id="">The standard should be extensible to later support other kinds of entity lookups beyond accounts.</li></ul></li><li id="">Allow an account to claim its preferred name (within a specified Name Service) for reverse lookups.some text<ul id=""><li id="">That claim should be verifiable from the Name Service.</li></ul></li><li id="">Allow both on and off-ledger lookups of a name, returning its associated account address.</li><li id="">Have all necessary name registration information stored on-ledger for full decentralization.some text<ul id=""><li id="">No required app-specific off-ledger API calls.</li></ul></li><li id="">Allow the operator of a Name Service to charge royalties for on-ledger name lookups or selectively authorize on-ledger lookups by badge.</li><li id="">Allow the operator of a Name Service full flexibility to define how their system enables registration and management of name associations and how the rights to manage names are controlled.some text<ul id=""><li id="">This includes the desired possibility of having control of a name linked to ownership of an NFT created by the system.</li></ul></li><li id="">Allow a Name Service to be associable with a dApp Definition using standard 2-way metadata linking.</li></ul><p id="">‍</p><h2 id=""><strong id="">Goals for Radix Wallet Adoption of the Standard</strong></h2><ul id=""><li id="">Allow users to easily specify a desired Name Service to use, via an on-ledger component address alone.</li><li id="">Identify and describe the Name Service to the user by the metadata set on a linked dApp Definition.</li><li id="">Allow users to enter a name string in place of a Radix account address and have it automatically resolved to an address returned by their preferred Name Service.</li><li id="">Display a name in place of a Radix account address – where the account has claimed a name to use, and that name’s association can be confirmed with a Name Service the wallet user has added.</li></ul><p id="">‍</p><h2 id=""><strong id="">Proposed Interface Standard</strong></h2><p id="">The proposed standard is as simple as possible, staying away from implementation details and differentiating features, and focusing only on the <strong id="">minimum method interface and metadata standards </strong>required to meet the goals above in a common way.</p><p id="">The concept of the standard is simply to standardize the lookup of name strings that each point to an account address. All else is implementation detail that need not be standardized. For example, a dApp may be expected to have its own unique systems to namespace their names and control the rights to add and modify names.</p><p id="">The proposed compliant Name Service system only includes two required parts:</p><ul id=""><li id=""><strong id="">A Name Service Provider component</strong> - Each Name Service deploys its own Name Service Provider component that implements a method and metadata standard and offers lookups against its own name records.</li><li id=""><strong id="">Account components</strong> – The owners of various accounts may wish to declare a discoverable name to use for that account, provided by a preferred Name Service Provider.</li></ul><p id="">The standards for these components are proposed as follows:</p><h3 id=""><strong id="">Name Service Provider Component</strong></h3><h4 id=""><strong id="">Metadata</strong></h4><p id="">To be compliant, a Name Service Provider component <strong id="">MUST</strong> apply the following metadata to self-identify as compliant:</p><figure id="" class="w-richtext-figure-type-image w-richtext-align-fullwidth" style="max-width:765px" data-rt-type="image" data-rt-align="fullwidth" data-rt-max-width="765px"><div id=""><img id="" alt="" src="/assets/66de12657ed0494925683871_AD_4nXdzFPMWWlsT5SCujs-yQMaoZJuC7p2dohVOMzEAoQZEUJWsbv9M2Zo_JNTTuBKY3in4wK2sf773a5HL9OJ4u16PZxNOLdCkvCeG4qBFKPBv82Pv_L1p6XSEyuNUGtYjAxjgpnaUjkE3V_dPfSsn1oUs1jVz.png" width="auto" height="auto" loading="auto"></div></figure><p id="">To provide the best user experience, a Name Service Provider component optionally <strong id="">MAY</strong> set metadata to associate itself to a dApp Definition in <a id="" href="https://docs.radixdlt.com/docs/metadata-for-verification">the standard way as for any other component</a>. in the Radix Wallet</strong></h5><ul id=""><li id="">User goes to the Radix Wallet’s preferences and chooses the “Add Name Service” option.</li><li id="">The user is given a field to enter a component address. The user chooses the option to use a QR code and scans a QR code provided by the Name Service website. <em id="">(They could of course alternatively simply copy the component address from the relevant website, if it is already on their mobile phon</em>e.)</li><li id="">The wallet looks up this component address and verifies that it has the component_type metadata field set to "name service provider."</li><li id="">The wallet sees that the component has a correctly confirmed link to a dApp Definition in its metadata, to a dApp called EZName.</li><li id="">The wallet lists EZName as a Name Service option and, because it is the first added, automatically sets it as the default to use when entering a name to lookup.</li><li id=""><em id="">(User can add additional Name Services in the same way, but one must always be selected as the default. Others will only be used as trusted Name Services for reverse lookups - more on this below.)</em></li></ul><p id="">‍</p><h5 id=""><strong id="">Using a name to send money to an account in the Radix Wallet</strong></h5><ul id=""><li id="">User has previously configured EZName as their preferred Name Service.</li><li id="">User arrives at the Radix Wallet’s “transfer” screen and taps to choose a recipient account.</li><li id="">In the account address field, user types “bob dobolina.”</li><li id="">The wallet calls EZName’s get_account_from_name method with "bob dobolina" as the name, and receives a return of acco...d85md2 (full address.)</li><li id="">The wallet shows that the name has been found and the user can proceed.</li><li id="">The name of the receiving account is shown as “bob dobolina”, and the address for that account is shown as acco...d83md2.</li><li id="">The transaction can be completed as normal, using that address.</li></ul><p id="">‍</p><h5 id=""><strong id="">Showing an account by its preferred name in the Radix Wallet</strong></h5><p id=""><em id="">(Note: this feature may be incomplete or not present in the initial Radix Wallet implementation.)</em></p><ul id=""><li id="">User has previously configured EZName as their preferred Name Service (see above.)</li><li id="">User arrives at the Radix Wallet’s “transfer” screen and taps to choose a recipient account.</li><li id="">User pastes in the address acco...d85md2.</li><li id="">The wallet checks this account and sees that it has correctly set both claimed_name (set to "bob dobolina") and claimed_name_service_provider metadata fields.</li><li id="">The wallet calls the indicated Name Service Provider component’s get_account_from_name with "bob. dobolina" and receives the response acco...d85md2 - a match for the address that claimed the name.</li><li id="">In the transfer summary, the wallet shows the name of the account as bob dobolina.</li></ul><p id="">‍</p><h5 id=""><strong id="">Setting a preferred name for one’s own account</strong></h5><ul id=""><li id="">User owns the name "funky.homosapien" on EZName (where EZName defines what exactly that ownership means.)</li><li id="">User logins in to the EZName dApp website; the website knows (however it defines it) that this is the user that owns "funky.homosapien".</li><li id="">User goes to an EZName page called “Claim Discoverable Name”, sharing their account acco...020nz3 with proof they own it.</li><li id="">User clicks on the website to request that "funky.homosapien" be set as the discoverable name for their account.</li><li id="">EZName website builds a transaction that sets the claimed_name metadata field on acco...020nz3 with "funky.homosapien" and sets the claimed_name_service_provider metadata field to the component address of the EZName name service provider.</li><li id="">User signs and submits the transaction in their Radix Wallet as normal.</li></ul><p id="">‍</p><h2 id=""><strong id="">Respond to the Call</strong></h2><p id="">The request for feedback is now closed.</p><p>‍</p><h2>Summary of Results</h2><p>This was an easy one! A little clarifying discussion on the <a href="https://discord.com/channels/417762285172555786/1282447252916535296/1282447252916535296">Discord thread for this topic</a> resulted in agreement to the proposed standard without any needed changes.</p><p>The RDX&nbsp;Works team is considering the standard proposed here to be good to go, and will be fitting implementation into the Radix Wallet roadmap as soon as feasible among other urgent priorities like MFA.</p><p id="">‍</p>
