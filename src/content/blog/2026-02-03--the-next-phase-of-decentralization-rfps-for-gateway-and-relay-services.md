<p id="">We recently outlined the <a id="" href="https://www.radixdlt.com/blog/2026-strategy-the-next-chapter-of-radix">2026 Strategy</a> and the <a id="" href="https://www.radixdlt.com/blog/the-foundation-operational-stack-mapping-the-2026-transition">Foundation Operational Stack</a>, making our direction clear: true decentralization is more than consensus alone, it’s the entire operational stack.</p><p id="">For a network to be resilient, it cannot rely on a single entity, including the Foundation, to host the infrastructure that allows users to interact with the ledger in a low friction way. We are now preparing the transition of critical auxiliary services to community and commercial operators.</p><p id="">The first step of this is opening Requests for Proposal (RFPs) for three core components: the <strong id="">Babylon Gateway</strong>, the <strong id="">Signalling Server</strong>, and the <strong id="">Connect Relay</strong>.</p><p id="">These are not grants for new experiments. These are contracts for experienced infrastructure operators to run the production-grade plumbing that powers the Radix Wallet, Dashboard and many other ecosystem services.</p><p id="">Here is the breakdown of the services and what is required.</p><h3 id=""><strong id="">Babylon Gateway</strong></h3><p id=""><strong id="">The Context:</strong> The Gateway is the entry point for almost all user-facing applications. It aggregates ledger data into a queryable PostgreSQL database and provides the API that wallets and explorers rely on.</p><p id=""><strong id="">The Requirement:</strong> We are seeking 1 or more operators to replace the current Foundation-run Gateway as a default provider.</p><ul id=""><li id=""><strong id="">Scale:</strong> Must handle the current ~2TB database with monthly growth of ~60GB.</li><li id=""><strong id="">Availability:</strong> Target 99.9% uptime. The current setup uses a Blue/Green deployment strategy to handle schema updates and re-indexing without downtime.</li><li id=""><strong id="">Performance:</strong> &lt;1s latency for standard queries, serving a global user base.</li></ul><p>‍</p><p id="">This is a heavy-lift role. It requires significant storage, robust DDoS protection, and the ability to manage complex database migrations without breaking service for the ecosystem.</p><p id=""><strong id="">Read the Babylon Gateway RFP on Radix Talk: </strong><a id="" href="https://radixtalk.com/t/foundation-rfp-babylon-gateway/2202">https://radixtalk.com/t/foundation-rfp-babylon-gateway/2202</a></p><h3 id=""><strong id="">Signalling Server</strong></h3><p id=""><strong id="">The Context:</strong> This is the "matchmaker" for the Radix Wallet. It establishes the peer-to-peer WebRTC connections between the mobile wallet and the desktop Chrome connector. It does not touch private keys or transaction payloads; it simply introduces peers.</p><p id=""><strong id="">The Requirement:</strong></p><ul id=""><li id=""><strong id="">Speed:</strong> &lt;300ms global latency is critical for the "instant" feel of Radix Connect.</li><li id=""><strong id="">Privacy:</strong> Strict "untrusted relay" principle. No payload inspection, no logging of encrypted data.</li><li id=""><strong id="">Architecture:</strong> Stateless design backed by Redis for session management. Must handle roughly 6,000 concurrent peak connections.</li></ul><p>‍</p><p id=""><strong id="">Read the Signalling Server RFP on Radix Talk: </strong><a id="" href="https://radixtalk.com/t/foundation-rfp-signalling-server/2204/1">https://radixtalk.com/t/foundation-rfp-signalling-server/2204/1</a></p><h3 id=""><strong id="">Connect Relay (RCR)</strong></h3><p id=""><strong id="">The Context:</strong> The Relay supports mobile-to-mobile connection between a mobile web browser and the Radix Wallet app. It buffers encrypted messages between the browser and the wallet.</p><p id=""><strong id="">The Requirement:</strong></p><ul id=""><li id=""><strong id="">Throughput:</strong> Efficient handling of small, encrypted payloads (instructions between browser and mobile).</li><li id=""><strong id="">Security:</strong> Aggressive rate limiting and TTL (Time-To-Live) settings (600s) to mitigate spam/DDoS while ensuring message delivery.</li><li id=""><strong id="">Privacy:</strong> Like the Signalling Server, this must operate as a blind relay. End-to-End Encryption (E2EE) is mandatory; the server must never see the raw data.</li></ul><p>‍</p><p id=""><strong id="">Read the Connect Relay RFP on Radix Talk: </strong><a id="" href="https://radixtalk.com/t/foundation-rfp-connect-relay/2203/1">https://radixtalk.com/t/foundation-rfp-connect-relay/2203/1</a></p><h3 id=""><strong id="">The Importance of P1 RFPs</strong></h3><p id="">These RFPs are the next logical step in the 2026 Strategy to decentralize the Radix network stack:</p><ol id=""><li id=""><strong id="">Removing Central Reliance:</strong> We are systematically removing the Foundation as the default provider for auxiliary services as we move to a community-led model.</li><li id=""><strong id="">Community-Led Operations:</strong> We are transferring control to the community. By engaging specialized operators, we ensure these services are maintained by those with the dedicated focus and expertise to run them sustainably.</li></ol><p id="">Any successful proposal must guarantee the current usage levels for core "public good" services like the Radix Wallet and Dashboard. However, we are interested in sustainable economic models that go beyond simple hosting.</p><p id="">We explicitly encourage proposals that commercialize access for additional heavy consumers, such as data aggregators, established dApps, or institutional integrators, to offset costs for the broader community. If you can monetize high-volume access to subsidize the public good, that is a win for the network.</p><p id="">If you have the hardware, the team, and the operational maturity to handle production traffic for a Layer 1 protocol, we want to see your proposal that we can present to the Radix Community to become a default provider for these services.&nbsp;</p><p id="">Review the technical specifications in the PDFs above and submit your proposal on RadixTalk using these links:</p><ol id=""><li id=""><a id="" href="https://radixtalk.com/t/foundation-rfp-babylon-gateway/2202/1">Gateway Service</a> - <a id="" href="https://drive.google.com/file/d/18m-Y5A2Te_1CJlVS8rww0HDHtbJvwg4O/view?usp=sharing">Full RFP</a></li><li id=""><a id="" href="https://radixtalk.com/t/foundation-rfp-connect-relay/2203/1">Signalling Service</a> - <a id="" href="https://drive.google.com/file/d/1g46o2xA1XJCW-KAGZClb-VlJE4j6WMtg/view?usp=sharing">Full RFP</a></li><li id=""><a id="" href="https://radixtalk.com/t/foundation-rfp-connect-relay/2203/1">Connect Relay</a> - <a id="" href="https://drive.google.com/file/d/1_dph1_1Ug_vBAxi8Jihc8dmlYPzOzQ0k/view?usp=sharing">Full RFP</a></li></ol><p id="">‍</p>
